Basic Matrix Multiplication in Python, Java and C:
How Matrix Size Drives Runtime and Memory

Abdelaziz Choukri Mohamed · Big Data 2026–2027, Grado en Ciencia e Ingeniería de Datos, Universidad de Las Palmas de Gran Canaria
Individual Assignment 1 — Basic Matrix Multiplication in Different Languages · 2026-10-17
Code, raw data and scripts: https://github.com/abdela758/bigdata-matmul

Abstract. This study measures how the matrix size n affects the runtime and the memory of the textbook triple-loop multiplication of dense n × n double matrices in Python, Java and C, on one Windows laptop (Intel Core i5-1135G7), with identical input files, loop order and timing protocol. Sizes were increased until a single multiplication exceeded 120 s: the largest size that met the budget was n = 1000 for Python, 2000 for Java and 2500 for C. All three implementations return bit-identical results. Kernel time (median and interquartile range over repeated batches and up to three process launches) grows roughly, but not exactly, cubically: the log-log slope over n = 100–1000 is 3.18 for Python, 3.39 for Java and 3.23 for C, and the time per inner iteration rises with n in every language, steeply in C and Java above n ≈ 1500. Python is about 67–78× slower than C (≈ 73× typically); Java is 1.2–1.7× slower than C up to n = 1000 but 4.9× slower at n = 1500. Peak process memory beyond the runtime baseline is about 7.9 bytes per matrix element in C, 8.6 in Java (plus a 42 MiB JVM baseline) and 40.7 in Python. The conclusions hold for these implementations, settings, inputs and this machine; the causes of the memory-related slowdowns were not measured with hardware counters and are discussed as hypotheses.

1. Introduction and objective

Multiplying two dense n × n matrices with three nested loops needs n³ multiply-add operations and is the standard starting point for talking about performance and scalability [1]. The algorithm is identical in every language, but the cost of each operation is not: an interpreter, a just-in-time compiler and an ahead-of-time compiler turn the same source into very different machine behaviour, and the way each language lays matrices out in memory decides how well the processor caches can help [2].

Research question. How does the matrix size n affect the runtime and the memory use of the textbook triple-loop multiplication of dense double matrices implemented in Python, Java and C, under one fixed and documented set of conditions on one machine? The factor that is changed is n (and, as a second factor, the language); the outcomes are the time of one multiplication and the peak memory of the process.

Predictions (formed from the algorithmic model and the course material before the final measurements; a small pilot was used only to choose sizes and limits, not to tune the code):

  1. P1 – cubic growth. While the working set stays in cache, the time of one multiplication grows like n³ in every language, so the log-log slope is about 3 and the time per inner iteration, t/n³, is roughly constant. Small sizes may sit above that line because of fixed overheads.
  2. P2 – constants differ by language. The constant should be far larger in Python (interpreted bytecode, boxed floats) than in Java or C; Java, after JIT compilation, should land in the same order of magnitude as C.
  3. P3 – memory effects at large n. In the i-j-k order the inner loop walks matrix B down a column, one cache line per iteration [2]. Once B (8n² bytes) no longer fits in the 1.25 MiB L2 cache (n ≈ 400) and then in the 8 MiB L3 cache (n ≈ 1000), t/n³ should rise, in all three languages.
  4. P4 – memory. C needs about 24n² bytes for the three matrices plus a small runtime; Java the same plus a larger JVM baseline; Python much more per element, because each element is a pointer to a separate 24-byte float object.

2. Background

Algorithm. For square matrices A and B, Cij = Σk Aik Bkj. Evaluating it directly takes Θ(n³) arithmetic operations [1]. In the loop order i-j-k used here, the inner loop reads A along a row (consecutive addresses) and B along a column (addresses n elements apart), which is the access pattern analysed by Drepper [2, Sec. 6.2.1].

Why the three languages should behave differently. CPython executes bytecode in an interpreter and represents every number as an object, so a list of floats stores pointers to separate float objects (24 bytes each in this interpreter). HotSpot starts in an interpreter, profiles the code and recompiles hot loops with its tiered JIT compilers; a double[][] is an array of row arrays holding unboxed 8-byte values. A C compiler produces native code before the program runs, and a malloced block holds the elements back to back. Compiler options matter: GCC enables, among others, loop interchange at -O3 [5], which could silently change the loop order, so the main comparison uses -O2.

Floating point. All three programs use IEEE-754 binary64 and the same operation order, so their results can be compared bit by bit. In general, different evaluation orders give slightly different sums; for a dot product of length n computed by recursive summation the error is bounded by γn Σk|aikbkj| with γn = nu/(1−nu) and unit roundoff u = 2−53 [3]; this bound is used as the numerical tolerance in Section 3.4.

3. Methodology

3.1 Implementations

The required algorithm, the straightforward triple loop with O(n³) work, is implemented in all three languages; no optimised library routine replaces the loops (NumPy is used only to check results, Section 3.4). The loops are, literally:

Python
for i in range(n):
    for j in range(n):
        s = 0.0
        for k in range(n):
            s += a[i][k] * b[k][j]
        c[i][j] = s

Java
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++) {
        double sum = 0.0;
        for (int k = 0; k < n; k++) sum += a[i][k] * b[k][j];
        c[i][j] = sum;
    }

C
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++) {
        double sum = 0.0;
        for (int k = 0; k < n; k++) sum += a[(size_t)i*n + k] * b[(size_t)k*n + j];
        c[(size_t)i*n + j] = sum;
    }

3.2 Inputs

All implementations read the same files A_n.bin and B_n.bin (raw little-endian binary64, row-major, values uniform in [0, 1)). They are generated with NumPy’s default_rng([20261012, n, which]), so each file is reproducible on its own, and their SHA-256 hashes are stored in inputs/checksums.json. Every language therefore multiplies exactly the same logical matrices; no language uses its own random-number generator.

3.4 Correctness validation

Before any benchmark, scripts/run_tests.py multiplies test matrices with each implementation and compares the result with references (Table 3 in Section 4.1 summarises the outcome). The checks are: identity and zero matrices (bit-exact); hand-computed 2 × 2 and 3 × 3 products (bit-exact); random integer-valued matrices stored as doubles, where every partial sum is exactly representable so any summation order must agree with NumPy’s integer product (bit-exact); random real matrices in [0, 1) and [−1, 1) and the shared benchmark inputs, compared (a) with an exact rational reference on 200 random entries and (b) with NumPy’s A @ B on all entries, against the bound γn Σk|aikbkj| of Section 2 (a result passes if the error is at most one bound against the exact value, and at most two bounds against NumPy, whose own rounding error is of the same size). Finally, the three implementations must return bit-identical matrices; this holds because they use the same operation order and no fused multiply-add (GCC’s default for -std=c11 is -ffp-contract=off [5]). The sum of all elements of C is also printed after every timed batch, which both proves that the computation ran and lets the checksums be compared across languages.

3.5 Timing protocol

  • What the timer includes. The multiplication kernel only. Input files are read, and the result matrix is allocated, before timing; the kernel assigns every element of C, so no initialisation is needed or timed. This is a kernel measurement, not an end-to-end one, and no end-to-end number is mixed with it.
  • Harness instead of JMH. The course material suggests JMH, pytest-benchmark and perf [4, 10]. Here one small harness with the same batching, warm-up, repetition and memory-measurement rules is used for all three languages, because the comparison needs the same timing boundary everywhere (perf is not available on Windows). Its behaviour is documented in this section and its raw output is kept; it was not cross-checked against JMH.
  • Clocks. Monotonic timers in each language (Section 3.1). In CPython on Windows perf_counter is backed by QueryPerformanceCounter (resolution 100 ns on this machine) [7], the same source as the C program [8].
  • Batches. To keep every timed interval much longer than the timer resolution, a batch executes m multiplications back to back and the program reports time per multiplication. m is found by doubling from 1 until a batch lasts at least 0.2 s (m = 1 whenever a single multiplication already takes longer). These calibration batches are also the first warm-up.
  • Warm-up and repetitions. After calibration, a configuration-specific number of warm-up batches is run (0–5; see config/experiment.json), followed by 5–15 measured batches. Warm-up and calibration batches are kept in the raw file but never enter a statistic. Five or more measured batches are collected for every configuration.
  • Launches. Each configuration is run in 1–3 separate processes (launches) so that process-level variation (JIT decisions, memory placement) is sampled, and the launches are interleaved in time: one sweep over all sizes and languages, then the next sweep with the language order rotated. Cheap configurations get three launches; the expensive ones, where one launch lasts minutes, get one or two, which is stated in Appendix A.
  • Summary statistics. All measured batches of all successful launches of a configuration are pooled. The central value is the median; variability is the interquartile range (IQR, quartiles by linear interpolation), reported as [Q1–Q3]. All raw measurements are kept in results/raw_samples.csv, and no observation was removed.
  • Dead-code protection. After each batch the sum of all elements of C is computed and printed; the multiplication function is not inlined in C (noinline) so that repeated calls in a batch cannot be merged.

3.6 Memory measurement

Metric: the peak working set of the whole process (PeakWorkingSetSize of PROCESS_MEMORY_COUNTERS_EX [9]) read by the driver with GetProcessMemoryInfo after the process ends, one value per launch; peak committed (private) bytes, PeakPagefileUsage, is recorded as well. It includes the language runtime, the loaded input data, the result and all temporary data, so it is not the same quantity as managed-heap use or as 24n² bytes of array storage, and the figures must not be compared as if it were. The runtime baseline is estimated from the smallest size (n = 10, three matrices of 800 bytes). Limits of the metric: working set counts resident pages only, the JVM reserves and touches memory in its own way, and a single peak per launch gives no information about when it occurred. CPU utilisation was not measured because it is not needed for the conclusions.

3.7 Sizes, budgets and fixed settings

The size sequence is roughly geometric (10, 20, 50, 100, 200, 300, 500, 700, 1000, 1500, 2000, 2500, 3000 where feasible) and avoids powers of two, whose large strides map matrix columns onto few cache sets and would confound the trend with an associativity effect. It spans the three regimes of P3 (B inside L2, inside L3, larger than L3). Budgets were declared before the final run: at most 120 s per single multiplication (a launch that prints nothing for 120 s is killed and recorded as a timeout), at most 30 min per launch and 4 GiB of memory (also the JVM heap cap). The largest size that met the limits is reported separately from the largest size attempted (Section 4.4); timeouts are reported as results at their limit and never given an invented time. Fixed in the main comparison: machine and power state, input files, loop order, numeric type, accumulator style, single-threaded kernels, timing boundary, batch rule, limits and, per language, the compiler/runtime settings in Table 1. For scale: three n × n binary64 matrices need 24n² bytes, 216 MB at n = 3000, far below the memory budget, so time, not memory, is the binding limit in this study.

4.3 Memory

Table 9 and Figure 3 show the peak working set. Every process has a runtime baseline that dominates at small n: 4.3 MiB for C, 10.8 MiB for Python and 41.8 MiB for Java. Above the baseline, C needs 7.8–8.0 bytes per matrix element at n ≥ 1000 (Table 10), i.e. exactly the 8 bytes of array storage per element of A, B and C. Java needs 8.2–12.9 bytes per element for n = 500–1000 (close to 8, plus its larger baseline; below that the net amount is too small to separate from baseline noise). At n = 1500 and 2000 its peak is the same, 136 MiB (14.7 and 8.3 bytes per element): the JVM grows its heap in steps, so the working set of the JVM does not track live data exactly; I did not investigate this further. Python needs 40.7 bytes per element (40.4–41.4), about five times C: each element is an 8-byte pointer to a separate float object of 24 bytes (sys.getsizeof(1.0)), and the figure is consistent with the allocator rounding that object up to 32 bytes (8 + 32 = 40) [6], although I did not verify the rounding in the interpreter source. As a result Python overtakes Java in total memory between n = 500 (40 vs 48 MiB) and 700 (67 vs 54 MiB), and at n = 1000 it uses 127 MiB against 66 (Java) and 27 (C).

4.4 Limits, timeouts and failures

The time budget was the only limit that bound. The largest size that met it was n = 1000 for Python (92.4 s per multiplication), 2000 for Java (82.3 s) and 2500 for C (68.8 s). One larger size was attempted per language (1500, 2500 and 3000); in each case a single multiplication ran past 120 s and the launch was stopped (Table 12). These are timeouts at the limit; their true times are unknown. For orientation only, extrapolating the Python time per iteration at n = 1000 to n = 1500 would give about 312 s, which is an extrapolation, not a measurement. No launch came close to the 4 GiB memory budget (the largest peak working set of any launch was 226 MiB), so there were no memory failures. A fourth launch also failed: launch 61 (second launch of Java at n = 1500) completed two batches (26.3 s per multiplication for the measured one) and then produced no output for more than 120 s; it was stopped after 824 s of wall time. I do not know why (a system suspend or heavy foreground activity are possible); its batches stay in the raw file but are excluded from every statistic, which is why Java at n = 1500 has a single launch.

4.5 Warm-up and variability

Warm-up matters only for Java (Figure 4, results/tables/warmup.csv). Its first batch is 23× slower than the measured median at n = 10, 3.4× at n = 100 and about 1× from n ≈ 300 on, which is why 5 warm-up batches were used for small sizes and why the first (calibration) batches are excluded from all statistics. For Python and C the first batch is within about ±30 % of the median at every size. Within a launch the times also drift: at n = 100 the C batches of the first launch become about 46 % slower between the first batches and the last measured ones (Figure 4), which is consistent with the CPU leaving its turbo frequency, but I did not record the clock frequency, so this is an interpretation. Pooling launches that ran at different times is meant to average over this.

The interquartile range of the pooled batches is 10 % of the median for the typical configuration (range 0.2–36 %; Appendix A). The widest ranges come from two launches that started while the machine was fully busy with something else (background CPU 100 % in the 0.5 s before the launch, background_cpu_percent): launch 24 (C, n = 700) was 51 % slower than the other launches of that configuration; launch 62 (C, n = 1500) was 31 % slower than the other launches of that configuration. They were kept (no observation was removed), and the medians stay close to those of the undisturbed launches because the other launches outnumber them. The median background load before launches was 13 % of all logical processors.

5. Discussion

Answer to the research question. Within the tested range, the time of one multiplication grows close to n³ but a little faster, in all three languages, and the language mainly changes the constant: about 73× between Python and C, and a factor of 1.2–1.7 between Java and C for n ≤ 1000, after the JIT has warmed up. Memory beyond a fixed runtime baseline grows with n² and the per-element cost is where the languages differ: about 7.9 bytes in C and 8.6 in Java, about 40.7 in Python.

P4: memory ≈ 24n² (C), + larger JVM baseline (Java), much larger per element (Python)confirmedC 7.9 B/element; Java 8.6 B/element + 42 MiB baseline (heap steps at 1500); Python 40.7 B/element.

Interpreting the memory-related slowdown (hypotheses, not tested). In the i-j-k order every inner iteration reads one element of B from a different row, so the loop touches n cache lines and n memory pages per column [2]. The gradual rise of t/n³ from small n and the steps at large n fit that picture, but my data do not identify the exact mechanism: the step comes later than the L3 capacity for C, and I had no hardware counters on this machine (perf, which the course material uses [10], is Linux-only). One possible explanation for the earlier and larger step in Java is its double[n][n] layout, which adds a row-header and row-pointer access to every iteration; the C program, by contrast, uses one contiguous block. Testing this would need a Java version with a flat array (and a C version with separate rows), which I did not run. The same applies to compiler flags: only -O2 was measured, and -O3 may reorder loops [5].

Other points. The JVM’s start is expensive (first batch 23× slower at n = 10), so Java’s steady state, which is what Table 4 reports, is not what a short program would see. The Python result is for the literal textbook loop on CPython 3.12.0; libraries such as NumPy or other implementations would change the constant by orders of magnitude, but that is a different experiment.

6. Limitations

  • One machine and one set of tools. A 15 W-class laptop CPU with turbo, Windows 11, CPython 3.12.0, OpenJDK 25.0.2 with default JIT/GC, GCC 16.2.0 at -O2. Other CPUs, operating systems, compilers or runtimes may give different constants and different step positions.
  • Uncontrolled machine state. The laptop was on AC power in the Balanced plan, but clock frequency and thermal state were not controlled or recorded, and the machine was not completely idle (background load is recorded for every launch). Two launches were visibly disturbed (Section 4.5).
  • Few launches at large sizes. The most expensive configurations have one launch (Python ≥ 700, Java ≥ 1500, C 2500), so launch-to-launch variation is unknown there; their IQR describes only the batches inside one process.
  • Memory metric. Peak working set includes the language runtime and depends on how the JVM and allocators grow their memory; it is not live data or array size, and one number per launch says nothing about when the peak occurs.
  • Kernel time only, one input type. Start-up, input and output are excluded; inputs are uniform in [0, 1) only; only square matrices were used.
  • No hardware counters. Explanations of the large-n behaviour are hypotheses.
  • Linux path untested. The driver also contains a Linux memory-measurement branch that was not run.

7. Conclusions

  • For the tested implementations, runtime grows roughly as n³ with a growing per-operation cost (slope 3.18–3.39 over n = 100–1000); the per-operation cost rises sharply in C and Java at n ≈ 1500–2000.
  • Python is about 73× slower than C at n ≥ 100; Java is 1.2–1.7× slower than C up to n = 1000 and 4.9× slower at 1500.
  • Memory: ≈ 7.9 bytes per element in C, ≈ 8.6 in Java and ≈ 40.7 in Python, on top of baselines of 4, 42 and 11 MiB (C, Java, Python).
  • Unresolved: why the steep step occurs where it does and why it is larger and earlier in Java; this needs layout variants and hardware counters, which were out of scope. No general claim that one language is faster than another follows from this study.
