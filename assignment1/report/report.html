Basic Matrix Multiplication in Python, Java and C:
How Matrix Size Drives Runtime and Memory

Abdelaziz Choukri Mohamed · Big Data 2026–2027, Grado en Ciencia e Ingeniería de Datos, Universidad de Las Palmas de Gran Canaria
Individual Assignment 1 — Basic Matrix Multiplication in Different Languages · 2026-10-17
Code, raw data and scripts: https://github.com/abdela758/bigdata-matmul

Abstract. This study measures how the matrix size n affects the runtime and the memory of the textbook triple-loop multiplication of dense n × n double matrices in Python, Java and C, on one Windows laptop (Intel Core i5-1135G7), with identical input files, loop order and timing protocol. Sizes were increased until a single multiplication exceeded 120 s: the largest size that met the budget was n = 1000 for Python, 2000 for Java and 2500 for C. All three implementations return bit-identical results. Kernel time (median and interquartile range over repeated batches and up to three launches) grows roughly, but not exactly, as n³: the time per inner iteration, t/n³, is nearly constant for small n and then rises in every language, steeply in C and Java above n ≈ 1000–1500. Python is about 73× slower than C (range 67–78× for n ≥ 100); Java is 1.2–1.7× slower than C up to n = 1000 but 4.9× slower at n = 1500, so in this study it does not approach C at large sizes. At n = 1000 the processes peak at 127 MiB (Python), 66 MiB (Java) and 27 MiB (C), on top of runtime baselines of 11, 42 and 4 MiB. The conclusions hold for these implementations, settings, inputs and this machine; explanations of the slowdown at large sizes are hypotheses, not measurements.

1. Introduction and objective

Multiplying two dense n × n matrices with three nested loops needs n³ multiply-add operations and is the standard starting point for talking about performance and scalability [1]. The algorithm is the same in every language, but the cost of each operation is not: an interpreter, a just-in-time (JIT) compiler and an ahead-of-time compiler turn the same source into very different machine behaviour, and the way each language lays a matrix out in memory decides how well the processor caches can help [2].

Research question. How does the matrix size n affect the runtime and the memory use of the textbook triple-loop multiplication of dense double matrices implemented in Python, Java and C, under one fixed and documented set of conditions on one machine? The factor that is changed is n (and, as a second factor, the language); the outcomes are the time of one multiplication and the peak memory of the process.

Expectations. They were written down from the algorithmic model and the course material before the final measurements were analysed, but after a small pilot run (used to choose sizes and limits) had already shown that large sizes cost more per operation, so they are informed expectations, not blind ones.

  1. E1 – cubic growth. The time of one multiplication grows like n³, so the time per inner iteration, t/n³, should be roughly constant, at least for small sizes.
  2. E2 – constants differ by language. The constant should be far larger in Python than in Java or C; Java, once the JIT has compiled the loop, should be in the same order of magnitude as C.
  3. E3 – memory effects. In the i-j-k order the inner loop walks matrix B down a column, which uses the cache poorly [2]. Once B (8n² bytes) outgrows the 1.25 MiB L2 cache (n ≈ 400) and then the 8 MiB L3 cache (n ≈ 1000), t/n³ may rise.
  4. E4 – memory. Every process has a fixed runtime baseline, and on top of it the data grow with n²; Python, which stores each number as a separate object, should need much more per element than C.

2. Background

Algorithm. For square matrices, Cij = Σk Aik Bkj; evaluating it directly takes Θ(n³) operations [1]. In the loop order i-j-k used here, the inner loop reads A along a row (consecutive addresses) and B along a column (addresses n elements apart), the access pattern analysed by Drepper [2, Sec. 6.2.1].

The three languages. CPython runs bytecode in an interpreter and stores every number as an object, so a list of floats holds pointers to separate 24-byte float objects. HotSpot (Java) starts in an interpreter, profiles the code and recompiles hot loops with its JIT compilers; a double[][] is an array of row arrays of unboxed 8-byte values. A C compiler produces native code before the program runs and a malloced block stores the elements back to back. GCC enables loop interchange at -O3 [4], which could silently change the loop order, so the main comparison uses -O2. All three programs use IEEE-754 double precision and the same operation order.

3. Methodology

3.1 Implementations

The straightforward triple loop with O(n³) work is implemented in all three languages; no optimised library routine replaces the loops (NumPy is used only to check results). The loops are, literally:

Python
for i in range(n):
    for j in range(n):
        s = 0.0
        for k in range(n):
            s += a[i][k] * b[k][j]
        c[i][j] = s

Java
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++) {
        double sum = 0.0;
        for (int k = 0; k < n; k++) sum += a[i][k] * b[k][j];
        c[i][j] = sum;
    }

C
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++) {
        double sum = 0.0;
        for (int k = 0; k < n; k++) sum += a[(size_t)i*n + k] * b[(size_t)k*n + j];
        c[(size_t)i*n + j] = sum;
    }

3.2 Inputs

All implementations read the same files A_n.bin and B_n.bin (binary double precision, row-major, values uniform in [0, 1)), generated with NumPy’s default_rng([20261012, n, which]). Each file is reproducible on its own, and its SHA-256 hash is stored in inputs/checksums.json, so every language multiplies exactly the same matrices.

3.4 Correctness validation

Before any benchmark, scripts/run_tests.py multiplies test matrices with each implementation: identity and zero matrices, hand-computed 2 × 2 and 3 × 3 products, and random integer matrices stored as doubles (exact in any summation order) must match bit for bit. Random real matrices (uniform in [0, 1) and [−1, 1)) and the shared benchmark inputs are compared with NumPy’s A @ B using an absolute and a relative tolerance of 10−9 (numpy.allclose). Double precision carries about 16 significant digits and summing a few hundred products only changes the last digits, so 10−9 is strict enough to catch any real error (a wrong index gives errors of order 1) while allowing the different summation order of NumPy’s library. Finally, the three implementations must return bit-identical matrices. The sum of all elements of C is also printed after every timed batch, which shows that the computation ran and lets results be compared across languages.

3.5 Timing and memory protocol

  • What is timed. The multiplication kernel only. Input files are read, and the result matrix allocated, before timing; the kernel assigns every element of C, so no initialisation is needed or timed. No end-to-end time is mixed with this kernel time.
  • Harness. The course material suggests JMH, pytest-benchmark and perf [3, 8]. Here one small harness with the same rules is used for all three languages, so that the timing boundary and the memory measurement are identical everywhere (perf is not available on Windows). It was not cross-checked against JMH. Timers are monotonic; in CPython on Windows perf_counter is backed by QueryPerformanceCounter (resolution 100 ns here) [5], the same source as the C program [6].
  • Batches. To keep every timed interval much longer than the timer resolution, a batch runs m multiplications back to back and the program reports time per multiplication; m is found by doubling until a batch lasts at least 0.2 s (m = 1 when one multiplication already takes longer).
  • Warm-up and repetitions. The calibration batches plus 0–5 further warm-up batches (config/experiment.json) are run first and never enter a statistic; then 5–15 measured batches. Each configuration is run in 1–3 separate processes (launches), interleaved in time; cheap configurations get three launches, the expensive ones one or two (Appendix A).
  • Statistics. All measured batches of all successful launches of a configuration are pooled. The central value is the median; variability is the interquartile range (IQR), shown as [Q1–Q3]. All raw measurements are kept in results/raw_samples.csv.
  • Memory. The peak working set of the whole process (PeakWorkingSetSize [7]), read by the driver after the process ends; one value per launch. It includes the language runtime, so it is not the same as array size or Java heap use, and the figures must not be compared as if they were. The runtime baseline is estimated from the smallest size (n = 10).

3.6 Sizes and budgets

Sizes grow roughly geometrically (10 … 3000, where feasible) and avoid powers of two. The budgets were declared before the final run: at most 120 s per single multiplication (a launch that prints nothing for that long is stopped and recorded as a timeout), 30 min per launch and 4 GiB of memory. The largest size that met the budget is reported separately from the largest attempted, and timeouts are reported at their limit, never with an invented time. Three n × n double matrices need 24n² bytes (216 MB at n = 3000), so time, not memory, is the limit that binds.

Cost per operation. If the cost were exactly cubic, t/n³ (Table 5, Figure 2) would be constant. It is nearly constant only for small sizes: Python stays at 63–66 ns up to n = 200 and C moves from 0.54 to 0.89 ns, Java from 0.84 to 1.08 ns for n = 50–200. After that it rises in every language: Python reaches 92 ns at n = 1000 (48 % above n = 100); C goes through 1.37 ns (n = 1000) and 1.61 ns (1500) to 3.54 ns (2000) and 4.40 ns (2500); Java through 2.38 ns, 7.9 ns and 10.3 ns. So the growth is cubic only approximately: close to cubic for small n, and clearly faster than cubic once the matrices are large.

Relative performance. Table 6 gives the ratios between languages. Python is 126× slower than C at n = 10, where fixed overheads weigh most, and 67–78× (median 73×) for n ≥ 100. Java is 1.18–1.20× slower than C for n = 100–300, 1.5–1.7× for n = 500–1000, and 4.9× and 2.9× at 1500 and 2000: after warm-up the JIT-compiled Java loop is close to C for small and medium sizes, but the gap grows, it does not close, at large sizes. The Java value at n = 1500 rests on one launch (the second launch failed, Section 4.4); the one measured batch of the failed launch, 26.3 s, is within 2 % of it.

4.3 Memory

Table 7 and Figure 3 show the peak working set. Each process has a fixed runtime baseline that dominates at small n: 4.3 MiB for C, 10.8 MiB for Python and 41.8 MiB for Java (the JVM is the heaviest). On top of it, the data grow with n²: at n = 1000 the growth above the baseline is 22 MiB in C, 24 MiB in Java and 116 MiB in Python, while the three matrices of 8-byte values alone need 22.9 MiB. C and Java stay close to that array size; Python needs about 5 times more because every element is a pointer to a separate float object. As a consequence Python’s total passes Java’s between n = 500 (40 vs 48 MiB) and n = 700 (67 vs 54 MiB), although Java starts 31 MiB higher. At n = 1500 and 2000 Java’s peak is the same, 136 MiB, while the array size grows from 51 to 92 MiB: its memory does not track the data exactly (probably because the JVM grows its heap in chunks; I did not investigate).

4.4 Limits, timeouts and failures

The time budget was the only limit that bound. The largest size that met it was n = 1000 for Python (92.4 s per multiplication), 2000 for Java (82.3 s) and 2500 for C (68.8 s). One larger size was attempted per language (1500, 2500 and 3000); in each case one multiplication ran past 120 s and the launch was stopped (Table 9). These are timeouts at the limit; their real times are unknown. No launch came close to the 4 GiB memory budget (largest peak 226 MiB), so there were no memory failures. A fourth launch also failed: launch 61 (second launch of Java at n = 1500) completed two batches and then produced no output for more than 120 s; it was stopped after 824 s of wall time. I do not know why. Its batches stay in the raw file but are excluded from every statistic, so Java at n = 1500 has a single launch.

4.5 Warm-up and variability

Warm-up matters mainly for Java (Figure 4): its first batch is 23× slower than the measured median at n = 10, 3.4× at n = 100 and about 1× from n ≈ 300 on, which is why the calibration and warm-up batches are excluded and 5 warm-up batches are used for small sizes. For Python and C the first batch is within about ±30 % of the median at every size. Times also drift inside a launch: at n = 100 the C batches of the first launch end about 46 % slower than they start, probably a frequency or thermal effect that I did not measure; pooling launches that ran at different times averages over it.

The IQR is 10 % of the median for the typical configuration (range 0.2–36 %; Appendix A). The widest ranges come from two launches that started while the machine was busy with something else: the C launch at n = 700 was 51 % slower than the other launches of that configuration; the C launch at n = 1500 was 31 % slower than the other launches of that configuration. They were kept (no observation was removed); the medians stay close to those of the other launches because those outnumber them.

5. Discussion

Answer to the research question. Within the tested range, the time of one multiplication grows close to n³ for small sizes and faster than that for large sizes, in all three languages (E1 only partly holds). The language mainly changes the constant: Python is about 73× slower than C, and Java 1.2–1.7× slower than C up to n = 1000 (E2 holds there), but 4.9× and 2.9× slower at n = 1500 and 2000. A statement that Java “approaches” C at large sizes would contradict these measurements. Memory has a fixed runtime baseline plus growth with n², and the languages differ in the per-element cost, not in the shape of the growth (E4).

Possible explanation of the rise in t/n³ (a hypothesis, not tested). In the i-j-k order the inner loop reads one element of B from a different row at every step, so it touches n cache lines per column [2]. B stops fitting in the L2 cache at n ≈ 400 and in the L3 cache at n ≈ 1000 (from the cache sizes), and the cost per operation rises in that region and beyond, which is consistent with a cache effect (E3). But the steepest steps come later (n ≈ 1500–2000 for C) or earlier (n ≈ 1000–1500 for Java) than those capacities, and I had no hardware counters to identify the mechanism. One possible reason for Java’s earlier and larger step is its double[n][n] layout, which adds a row-pointer access to every iteration, but that would need a separate experiment (a flat Java array, a C version with separate rows) that I did not run.

Other points. Java’s steady state, which Table 4 reports, is not what a short program would see, because the first batches are up to 23× slower. The Python result is for the literal textbook loop on CPython 3.12.0; libraries such as NumPy would change the constant by orders of magnitude, but that is a different experiment.

6. Limitations

  • One machine and one set of tools: a thin-and-light laptop CPU with turbo (HP 250 G8, i5-1135G7), Windows 11, CPython 3.12.0, OpenJDK 25.0.2 with default JIT/GC, GCC 16.2.0 at -O2. Other hardware, operating systems, compilers or runtimes may give other constants and other step positions.
  • Machine state not fully controlled: AC power and the Balanced plan, but clock frequency and thermal state were not controlled or recorded and the machine was not completely idle; two launches were visibly disturbed (Section 4.5).
  • Few launches at large sizes: the most expensive configurations have one launch (Python ≥ 700, Java ≥ 1500, C 2500), so launch-to-launch variation is unknown there.
  • Memory metric: the peak working set includes the language runtime and depends on how each runtime grows its memory; it is not live data or array size.
  • Kernel time only, one input type: start-up, input and output are excluded; inputs are uniform in [0, 1); only square matrices; no hardware counters, so explanations of the large-n behaviour are hypotheses.

7. Conclusions

  • For the tested implementations, runtime grows roughly as n³ for small sizes; the cost per operation then rises in all three languages, steeply in C and Java above n ≈ 1000–1500.
  • Python is about 73× slower than C for n ≥ 100. Java is 1.2–1.7× slower than C up to n = 1000 and 4.9× slower at 1500 (single launch).
  • Memory is a fixed runtime baseline (4, 42 and 11 MiB for C, Java and Python) plus growth with n²; at n = 1000 Python needs about 5 times the array size, C and Java about once.
  • Unresolved: why the steep step occurs where it does and why it is earlier and larger in Java; this would need layout variants and hardware counters. No general claim that one language is faster than another follows from this study.
